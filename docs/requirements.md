# Requirements and acceptance criteria

## Functional requirements

1. A supervisor classifies a request into operations, customer service, knowledge base, or review analysis and supports more than one specialist in a plan.
2. Typed tools expose product, order, inventory, customer-feedback, and permitted messaging operations through a provider interface.
3. The default Amazon provider uses local sample data and never requires credentials.
4. Customer-service processing distinguishes FAQ, order, logistics, after-sales, and human-handoff outcomes.
5. The RAG module preserves document metadata, supports hybrid retrieval contracts, reranking, citations, and a refusal path when evidence is insufficient.
6. Memory isolates conversations by user and session and distinguishes short-term context from durable preferences.
7. Reliability captures request IDs, retry policy, checkpoints, tool traces, token/latency fields, and failure classification.
8. Evaluation assets cover route correctness, tool selection and arguments, RAG quality, and recovery/idempotency.

## Deterministic boundaries

- Authentication, authorization, tenant isolation, idempotency, and outbound messaging availability are ordinary code decisions.
- LLM output cannot directly send a message, issue a refund, or modify an order.
- A buyer-message action must first be returned by the provider's available-actions operation and must be confirmed by an operator in the demo contract.
- Missing evidence produces a refusal or human handoff instead of an invented answer.

## Acceptance evidence

- Repository audit reports every required module and file.
- Python syntax compilation succeeds.
- Evaluation datasets conform to documented schemas.
- Example reports contain `result_status: illustrative`, unless generated by an actual run with provenance.
- `THIRD_PARTY_NOTICES.md` exists and excluded licenses are documented.
