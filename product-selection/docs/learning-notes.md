# 选品工作台学习账本

这份文件持续记录项目过程中提出的概念问题。项目完成后，再整理为最终复盘与面试讲解稿。

## 阶段一：本地运行与项目骨架

- **本地开发服务**：在自己的电脑上运行前端和后端，供开发、调试和验证使用；目前前端与 BFF 分别由项目脚本启动。
- **mock**：按照真实数据结构生成的假数据，用于离线开发和演示；能证明流程可运行，不能证明市场结论真实。
- **`.env.example` 与 `.env`**：前者是可提交的配置模板，后者保存本机真实密钥并被 Git 忽略。环境变量通常在进程启动时加载，修改 `.env` 后需要重启服务。
- **Git diff**：查看修改前后的差异；`-` 是修改前，`+` 是修改后。
- **Cursor 快速操作**：`Ctrl+P` 找文件，`Ctrl+F` 搜当前文件，`Ctrl+Shift+F` 搜整个项目，内置终端用于运行项目命令。

## 阶段二：前端、后端与接口边界

- **API/接口**：约定请求地址、输入、输出和错误的程序入口。本项目的 `/api/search` 等是自己的后端接口，接口内部再调用外部服务。
- **BFF**：专门服务前端的后端层。它保存密钥、校验请求、调用 Tavily/SerpApi、整理结果，再把安全且稳定的数据返回前端。
- **Pipeline**：后端业务流程的组织者，负责按顺序启动步骤、更新进度和处理中止；具体搜索与计算由各步骤和 DataSource 完成。
- **Tavily 与 SerpApi**：Tavily 用于发现互联网资料；SerpApi 用于取得 Google、Google Trends、Amazon 等搜索结果。`fetch` 是发出 HTTP 请求的方式，它们是提供数据的外部服务。
- **HTTP 与 HTTPS**：HTTPS 是加密并验证服务器身份的 HTTP。公网登录、上传和普通接口都应使用 HTTPS；本机 `localhost` 开发可使用 HTTP。
- **HTTP 方法与 `fetch` 的区别**：GET、POST、PUT、PATCH、DELETE 等是 HTTP 请求方法；`fetch` 是 JavaScript 用来发出 HTTP 请求的内置函数，不是第三种请求方法。本项目中，前端用 `fetch` + POST 请求自己的 `/api/listings`，后端再用 `fetch` + GET 请求 SerpApi。

## 阶段三：真实 Tavily `/api/search`

- **完整数据链路**：前端传入关键词 → 后端接口读取并校验 → `JSON.stringify` 把 JavaScript 对象变成 JSON 文本 → `fetch` 调用 Tavily → `response.status` 判断 HTTP 成功或失败 → `response.json()` 把 JSON 变成 JavaScript 对象 → 映射为 `{ title, url, snippet }[]`。
- **异步与 `await`**：`fetch` 先返回 Promise；`await` 等待当前请求的结果，但不会让整个 Node.js 后端停止处理其他工作。
- **JSON 序列化**：JavaScript 使用 `JSON.stringify(object)` 把对象变为 JSON 文本并通过 HTTP 发送。
- **JSON 反序列化**：JavaScript 使用 `JSON.parse(text)` 把 JSON 文本变回对象；`response.json()` 会读取响应并完成这一解析。
- **Python 对照**：`json.dumps(data)` 把 Python 对象变为 JSON，`json.loads(text)` 把 JSON 变为 Python 对象；`requests.post(json=data)` 和 `response.json()` 可分别自动处理两个方向。
- **HTTP 状态码与错误传递**：Tavily 返回 401、429、500 等状态，后端通过 `response.status` 取得，再转换成自己的接口错误返回前端。浏览器 Network、页面错误、接口测试和后端日志是常见定位入口。
- **真实开发排错**：`EADDRINUSE` 表示端口被占用。本次通过错误信息、端口、PID、接口响应逐层定位到旧后端进程；旧进程没有重新读取后来填写的 `.env`。
- **npm 脚本**：`npm run dev:bff` 是让 npm 执行 `package.json` 中名为 `dev:bff` 的脚本，实际由 Node.js 加载 `.env` 并运行 `server/index.mjs`。
- **`npm run dev`**：不是“运行 npm 这个软件本身”，而是让 npm 查找 `package.json` 的 `dev` 脚本。本项目的 `dev` 会同时启动后端 BFF 和前端 Vite 开发服务。
- **`localhost` 与端口**：`localhost` 表示“当前这台电脑”，通常等价于 `127.0.0.1`，外部用户不能通过这个地址访问你的项目。冒号后的 `5273` 是当前项目为前端指定的端口，不是固定标准；常见的 `5173`、`3000`、`8000`、`8787` 都只是不同程序选择的端口。本项目使用前端 `5273`、后端 `8787`。
- **语法正确不等于业务正确**：语法检查能发现非法字符，却无法发现 `Bearer` 后缺少空格等合法但错误的业务写法，还需要测试真实行为。
- **确定性品类画像**：第一版 `/api/profile` 不调用 LLM，只把英文关键词和真实搜索来源整理为固定结构。纯中文、非 US 市场或没有真实来源时拒绝生成，避免伪造翻译或无证据结论。

## 阶段四：真实 Amazon 商品

- **商品映射**：把 SerpApi 的第三方数据格式整理为项目内部的 `CompetitorListing` 格式。对应关系是 `asin → id`、`extracted_price → price`、`reviews → reviewCount`、`link_clean → url`，并补充 `channel: 'amazon'` 和 `currency: 'USD'`。
- **映射与 `.map()`**：映射是一种数据转换思想；JavaScript 的数组 `.map()` 是批量完成映射的方法。统一内部格式后，即使以后把 Amazon 换成 Walmart，前端和 Pipeline 也不用跟着认识每家外部接口的字段。
- **JSON 解析不等于业务映射**：`JSON.parse()` / `response.json()` 只负责把 JSON 文本变成 JavaScript 对象；映射发生在解析之后，负责把第三方字段翻译成项目字段，例如 Walmart 的 `product_id → id`、`primary_offer.offer_price → price`，同时完成价格清洗、无效商品过滤和渠道标记。可以记成：解析解决“电脑能读”，映射解决“项目能用”。
- **价格清洗**：外部接口有时返回数字，有时返回 `$1,299.50` 这样的字符串。后端统一转换为数值 `1299.5`，无有效价格的商品不进入市场计算。
- **商品去重**：优先按 ASIN 去重，同时按去掉多余空格且忽略大小写的标题去重，避免多个检索词返回同一个商品后重复计算。
- **限并发**：多个检索词分批调用 SerpApi，每批最多同时请求 3 个。这样兼顾速度，也降低触发限流或给外部服务造成瞬时压力的风险。
- **旧服务进程问题**：修改后端代码后，已经运行的 Node.js 进程不会自动加载新代码；必须重启。此次真实验证先发现 8787 上的旧进程仍返回 SerpApi 原始 JSON，按端口和 PID 停止后重启，才验证到新的统一商品格式。
- **四个后端接口的分工**：`/api/search` 通过 Tavily 搜公开网页背景；`/api/profile` 把搜索资料整理成品类画像；`/api/listings` 通过 SerpApi 搜 Amazon 商品；`/api/trend` 通过 SerpApi 查询 Google Trends 热度。页面进度由 Pipeline 管理，不是 Tavily 管理。
- **品类画像**：可以理解成“品类身份证”和后续步骤的统一输入。以 `women yoga pants` 为例，包含规范名称、Amazon/Google Trends 可使用的英文检索词、长尾词、简短说明和真实网页引用。
- **Google Trends 热度**：表示某个词在指定地区和时间范围内的相对关注度，范围通常为 0～100；100 是该范围内的最高点，不代表 100 次搜索，也不是商品销量。
- **趋势数据映射**：SerpApi 返回每周的 `timestamp` 和 `extracted_value`；接口先按 `YYYY-MM` 聚合成月均热度，再交给 Pipeline 计算走向、同比和季节峰值，避免把 12 周误当成 12 个月。
- **Tavily 与 Google Trends 的区别**：Tavily回答“网上有哪些背景资料和证据网页”；Google Trends回答“一个搜索词随时间是变热还是变冷”。前者产出网页，后者产出时间序列。
- **第一次 live 成功证据**：学习者在 Chrome 输入 `women yoga pants`，四个 Pipeline 步骤全部变绿，总耗时约 10.9 秒；得到 125 个在售 listing、真实趋势和 44 分报告。这证明四接口和完整流程已经连通，不代表当前商业评分已经可信。
- **“跑成功”与“结论可信”是两层验收**：接口没有报错、Pipeline 全绿、报告生成，叫技术流程成功；数据是否完整、公式是否合理、结论能否用于决策，还需要业务验收。首次报告需求量为 0，是因为 Amazon 结果没有精确 `monthlySales`；利润分目前只使用中位售价，没有采购、物流、佣金和广告成本。
- **界面可选择不等于后端已经支持**：首次截图同时点亮了 Amazon 和 Walmart，但第一版 `/api/listings` 目前只实现 Amazon；125 个 listing 不能解释成两个渠道的数据。UI 选项与后端能力不一致属于需要在 Review 中修正或明确提示的产品问题。
- **纯中文品类为什么失败**：Tavily 搜索后，第一版确定性 `/api/profile` 会主动拒绝不含英文字母的关键词，错误是“第一版请输入英文品类关键词”。这不是只能搜索 `women yoga pants`；`jeans`、`hoodies`、`cargo pants`、`denim jacket` 等英文服装品类都能使用。`clothes`、`pants` 等过宽词虽然可能运行，但样本混杂、结论价值较低。
- **真实工程判断也要记录**：实现过程中发现的数据粒度不匹配、外部字段缺失、旧进程、限流、错误降级、技术成功但业务结论不可信等问题，都属于重要工程判断，必须记录到学习账本，并在最终复盘中说明“发现了什么、为什么重要、如何处理”。

## 阶段四 Review 与 Git 分支

- **为什么先建分支再改代码**：正常流程从稳定的 `main` 创建功能分支，在分支开发、测试和 Review，通过后再合并。这样主分支保持可运行，也方便比较、撤回和多人协作。本项目早期练习改动直接堆在本地 `main`，属于流程欠缺；现已把未提交改动原样带到 `codex/stage4-live-review`，后续不再直接修改 `main`。
- **Code Review 是什么**：在代码合并前，由作者以外的人检查“改了什么、为什么改、是否正确、有没有副作用、测试是否覆盖、有没有密钥或无关改动”。Review 不是只看代码能不能运行，也要检查业务含义是否诚实。
- **第一次人工 Review 分工**：AI 是本次修复的作者，学习者是 Reviewer。学习者重点查看 `market.ts`、`trend.ts`、`scoring.ts` 的 diff，判断无品牌集中度、日历月份和缺失数据提示三项修改是否符合预期；AI提供测试证据，但不能代替人工判断。
- **测试与 Review 的区别**：测试自动验证已写明的预期；Review 可以发现“测试没有想到的问题”、需求理解偏差、命名误导和不必要的复杂度。两者都通过，代码才更值得合并。
- **Review 到底看什么**：不只看语法和代码逻辑，还看是否满足需求、数据含义是否真实、异常路径、安全与密钥、性能、维护成本、测试覆盖、改动范围，以及前端承诺是否与后端能力一致。本次学习者完成的是业务逻辑 Review。
- **渠道能力必须前后端一致**：第一版后端只实现 Amazon，因此前端固定选择 Amazon，不能取消；Walmart/TikTok 保留为禁用的“进阶版”入口。后端也会拒绝空渠道或非 Amazon 渠道，避免页面之外的请求被静默当成 Amazon 处理。

## 真实故障案例：Chrome 能联网，但后端 `fetch failed`

- **现象**：页面的 `/search` 和 `/listings` 返回 500 `fetch failed`，`/trend` 返回 502“SerpApi 趋势连接失败”；后续步骤因为缺少市场或趋势数据而无法给出结论。
- **判断方法**：如果 Key 错误，外部服务通常已经收到请求并返回 401 或 403；`fetch failed` 且底层为 `UND_ERR_CONNECT_TIMEOUT`，表示后端在取得 HTTP 响应前就连接超时，优先检查 DNS、443 网络、代理、VPN 和证书。
- **根因**：Windows/Chrome 使用本机代理 `127.0.0.1:7890`，但 Node 后端默认直接联网，没有使用该代理。因此 Chrome 能打开网页，不代表后端 `fetch` 也一定能联网。
- **修复**：本地 `.env` 保存 `HTTP_PROXY`、`HTTPS_PROXY`；`dev:bff` 使用 Node 的 `--use-env-proxy` 启动参数。代理地址属于本机环境配置，不提交 Git。
- **验证证据**：修复前 Node 连接 Tavily 和 SerpApi 均出现连接超时；使用代理后两个站点都返回 HTTP 200，本地 `/api/search`、`/api/listings`、`/api/trend` 均成功返回。
- **错误传播链**：外部连接超时 → 后端 `fetch` 抛出异常 → BFF 转成 500/502 JSON → 前端 `post()` 抛错 → Pipeline 把对应步骤标红 → 结论步骤因依赖数据缺失而停止。这属于真实开发中常见的网络环境排错问题。
- **Clash 系统代理与 TUN**：`127.0.0.1:7890` 是 Clash 在本机监听的代理端口；Windows 的 `ProxyEnable=1` 只能证明系统代理已开启，不能单独证明 TUN 正在接管所有程序流量。此次 Node 直连仍超时，说明它没有被当前 TUN 路径有效接管，需要显式读取 `HTTP_PROXY`、`HTTPS_PROXY`。
- **Codex 与 Cursor 的分工**：Codex 桌面端可以加载工作区，让 AI 读取、修改文件并通过受控本地 Shell 执行 PowerShell 命令；Cursor 是完整 IDE，更适合学习者自由浏览整个文件树、手动编辑和使用持续交互式终端。只让 AI 开发和按链接查看文件时可以只用 Codex；需要大量亲手写代码和自由逐文件浏览时，Cursor 仍更顺手。

## 阶段五：测试与 CI

- **自动化测试**：把预期行为写成可重复执行的检查。本项目使用 Node.js 内置测试框架，运行 `npm test` 会自动发现 `*.test.mjs`，测试字段映射、价格清洗、去重、趋势聚合、市场计算和评分提示。
- **CI（持续集成）**：代码 push 或创建 PR 后，由 GitHub 的云端机器自动安装依赖、执行类型检查、测试和构建。CI 变绿表示这套自动检查通过，不等于业务一定正确，所以仍需要人工 Review。
- **为什么 CI 不调用真实 API**：真实外部请求会消耗额度、受网络波动影响，还需要暴露密钥。CI 使用代码内的脱敏 fixture，只测试映射和业务逻辑，因此结果稳定且不需要 Tavily、SerpApi Key。
- **本地测试与 CI 的关系**：本地先运行同一套命令，尽早发现问题；push 后 CI 在一台干净的 Linux 机器上重新验证，避免“只在我的电脑上能运行”。

## PR 独立 Review 与外部服务错误

- **为什么让独立子 Agent Review**：作者容易沿着自己的实现思路检查，独立 Reviewer 没有参与编码，更容易发现测试未覆盖、业务含义不诚实和边界不一致的问题。本次它发现了“数据不全却仍给分”“Amazon 空结果仍返回成功”“界面仍能选非美国市场”“本地服务监听范围过大”四项问题。子 Agent 适合边界清楚、可独立完成的只读审查；不应让多个 Agent 同时修改同一文件。
- **人工 Review 不是只看几行代码**：学习者不必逐行审阅所有机械测试，但必须理解并确认需求范围、核心业务规则、数据真实性、异常提示、安全边界和前后端承诺是否一致；AI 和自动化测试负责覆盖重复性的字段、分支和构建检查。
- **502 与 504 的区别**：在 `server/external-request.mjs` 中，`timedOut ? 504 : 502` 是后端对外部服务故障的映射。等待 Tavily 或 SerpApi 超时返回 504 Gateway Timeout；连接失败或没有取得有效响应返回 502 Bad Gateway。它们先出现在本项目 BFF 返回给前端的 HTTP 响应中，随后可在浏览器 Network、页面错误和接口测试里看到。
- **为什么缺数据要返回“数据不足”**：没有月销量和完整成本时，程序即使能计算出一个数字，也没有足够证据支持“建议/不建议”。因此第一版把总分设为 `null`、页面显示“—”，并把决策标为 `insufficient`；趋势只陈述观察到的高峰月份，不再给出“提前备货”等操作建议。
- **为什么 Amazon 空结果不能当成功报告**：第三方请求返回 HTTP 200 只代表请求执行成功，不代表获得了可分析的数据。映射和清洗后没有任何有效商品时，`/api/listings` 返回 422，告诉前端“请求格式没错，但这些数据无法完成业务分析”。

## 阶段 7A：进阶核心版

- **单位经济模型**：不再把商品售价叫作利润。项目用 Amazon 样本中位售价，减去采购成本、头程物流、平台佣金和广告费，得到单件利润；`毛利率 = 单件利润 ÷ 售价`。学习者亲手确认了固定案例：售价 40、采购 12、头程 4、佣金 15%、广告 10%，单件利润为 14，毛利率为 35%。
- **需求代理**：优先使用真实月销量；拿不到时，可用评价数中位数作为观察信号，但页面和报告必须明确写“评价数不等于销量”，可信度最高只能到中等。代理指标是有限证据，不能包装成真实业务数据。
- **分位数价格带**：按排序后样本所在位置切成低、中、高三组，比固定宽度分箱更适合价格长尾明显的商品样本；样本少于 3 个时只生成一组，避免假装精细。
- **可信度与数据完整度**：总分回答“这个品类看起来怎样”，可信度回答“这份结论有多少证据支撑”。当前综合样本量、引用来源、数据时间、成本是否完整和需求信号类型，并列出缺失项。
- **降级不是伪造**：Google Trends 失败时，可以去掉趋势维度并对剩余权重重新归一化，但必须显示“趋势数据缺失”和 partial；商品为空、成本非法或需求信号完全缺失时，不输出商业建议。
- **TDD 红灯到绿灯**：先用测试写清固定利润结果和非法输入，再看到“单位经济模型未实现”的失败；实现公式后重跑，测试从红灯变绿。失败测试证明测试确实能抓住功能缺失，不是为了凑数量。
- **Node 测试与 TypeScript import 差异**：Node 24 直接运行 TypeScript 测试时，相对 import 需要明确 `.ts` 文件名；项目原来的 TypeScript 配置又默认禁止该后缀。本次通过 `allowImportingTsExtensions` 统一两边要求，最终类型检查和测试同时通过。
- **阶段分工**：学习者亲手创建分支、确认公式、定义 `CostInputs`、写利润测试并运行红灯测试；AI补齐计算实现、需求代理、分位数、可信度、Pipeline 接线、页面解释和边界测试。Chrome 验收、人工 Review、Git diff、commit、push、PR 和 CI 仍由学习者亲手完成。

## 阶段 7B：DeepSeek Prompt 与结构化输出

- **Prompt 是什么**：Prompt 就是提示词，是程序发送给大模型的任务说明。System Prompt 是其中优先级较高、相对固定的一层，用来规定模型的角色、任务、输入含义、业务边界和输出要求；用户每次输入的关键词和证据则属于动态输入。
- **DeepSeek API 是怎样请求的**：BFF 在 `server/deepseek.mjs` 使用 Node 原生 `fetch()` 向 DeepSeek Responses API 发送 `POST` 请求；请求头通过 `Authorization: Bearer DEEPSEEK_API_KEY` 携带服务端密钥，请求体包含模型名、System Prompt、用户关键词、证据和 JSON Schema。返回内容先经过 `JSON.parse()`，再交给 `validateCategoryProfile` 做业务验收；通过后进入 Pipeline，失败则有限重试或明确降级到确定性画像。它和请求 Tavily、SerpApi 的本质相同，都是服务端 HTTP API 调用，只是输入、输出和验收规则不同。
- **第一次 DeepSeek live 证据**：学习者在本机 `.env` 配置 Key 后，AI 使用脱敏的 `women yoga pants` 输入发起一次真实 DeepSeek API 请求；返回 `mode=deepseek`、`degraded=false`，得到规范品类名、3 个搜索词、2 个相关词、中文摘要和 2 条由服务端 evidence ID 映射的引用。密钥未打印、未写入前端或 Git。该证据证明画像 live 链路跑通，不代表模型摘要在所有输入上都一定正确。
- **DeepSeek 不负责连接电商平台**：Amazon 和 Walmart 商品由 SerpApi 对应引擎获取，TikTok 商品由官方 Affiliate Marketplace API 获取，Google Trends 也由 SerpApi 获取，公开网页证据来自 Tavily；DeepSeek 只负责理解文字证据、规范品类名称、扩展适合平台搜索的英文词、生成摘要并声明 evidence ID。TikTok 代码已经接入，但 live 仍需要 Seller 授权，不能因为使用了大模型就写成“三平台 live 已连接”。
- **连接大模型的意义**：固定规则只能机械生成类似“关键词 + outfit/plus size”的词；大模型能结合证据识别 `high waisted`、`plus size`、`yoga leggings` 等真实细分表达，提高后续 Amazon/Walmart 搜索的覆盖和品类摘要可读性。它不能代替商品 API，也不能凭空提供销量、价格和平台事实。
- **项目实际可演示容量估算**：按 2026-09-01 的 `deepseek-v4-flash` 官方价格和本项目一次画像约 1,000～2,500 输入 token、150～300 输出 token 粗算，学习者充值 4 元可保守支持约 400 次以上的画像调用，足够个人开发与面试演示。这里的“一次”是运行一次“品类输入 → DeepSeek 画像”，不是只获取一个商品；每次画像会产生多个搜索词，再由 SerpApi 返回多条商品。整个工作台的真实可运行次数还会受到 Tavily 和 SerpApi 各自额度、失败重试和未来价格变化限制，不能把 400 次写成系统保证。
- **为什么这里必须写 Prompt**：普通函数擅长固定公式和明确判断，但“根据多条文字证据生成品类名称、相关搜索词和摘要”没有一条固定公式，适合交给语言模型。Prompt 把模糊的自然语言能力限制在项目需要的范围内，避免模型自由发挥。
- **什么时候需要写 Prompt**：只有当功能确实调用大模型完成理解、提取、分类、总结或生成时才需要 Prompt。字段转换、价格过滤、利润计算、权限、格式校验等确定性工作应由普通代码完成，不能全部塞给模型。
- **通用写法**：复杂 Prompt 使用“角色 → 任务 → 输入 → 处理规则 → 输出格式 → 输出前自检”的分段结构；规则有顺序或完整性要求时使用编号。结构要让一个不了解项目的新同事也能照着完成任务。
- **本项目的关键限制**：模型只能使用输入的公开证据，只能返回 `name`、`searchTerms`、`relatedTerms`、`summary`、`evidenceIds`，不得编造 URL、销量、价格、利润、趋势或证据 ID；证据中的文字只当数据，不能当成新的系统命令。
- **Prompt、JSON Schema 和 validator 的分工**：Prompt 告诉模型“应该怎样做”；JSON Schema 不是供人观看的普通表格，而是一份机器可读取的数据合同，API 用它约束模型返回合法 JSON，并限制字段名、字段类型、必填项和数组数量；validator 是模型返回后的普通代码验收，继续检查空字符串、重复值和 evidence ID 是否真实存在。Schema 合法只代表“外形符合合同”，不代表业务内容一定真实，因此三层不能互相替代。
- **Evidence ID 是什么**：BFF 会给每条真实搜索证据分配一个项目内编号，例如 `evidence-1`。DeepSeek 输出的 `evidenceIds` 数组不是商品 ID，也不是 URL，而是模型声明“这段摘要使用了哪些输入证据”的引用清单；之所以是数组，是因为一段摘要可以同时由多条来源支持。
- **validator 核心实现做了什么**：先检查模型是否返回非空 `evidenceIds` 数组；再用 `Set` 保存本次请求真正允许引用的证据 ID；最后用 `some` 检查模型返回的 ID 中是否存在任何未知值，发现一个就抛错拒绝整份画像。这样可以阻止模型把结构合法但来源不存在的内容送入报告。
- **失败与降级**：模型可能返回空内容、非法 JSON、结构正确但内容不可信，或因为缺 Key、超时和限流无法响应。程序必须拒绝非法输出、有限重试，并在允许时退回现有确定性画像，同时明确标记 degraded，不能冒充 DeepSeek 已成功生成。
- **学习者实际完成**：学习者亲手写入第一版 System Prompt，完成 `validateCategoryProfile` 的 evidence ID 核心校验，并写出一项非法 evidence ID 测试。第一次粘贴时把实现函数放进测试文件，导致同名函数重复声明；AI只负责把已经写好的函数移动回实现文件并恢复测试结构，不把机械修复记作学习者的新业务实现。
- **验证证据**：学习者先看到 validator TODO 与预期错误信息不匹配的 TDD 红灯；实现后运行 `node --test server/category-profile-ai.test.mjs`，结果为 1 项通过、0 项失败，证明不存在的 evidence ID 会被拒绝。项目结束时把“为什么写 Prompt、什么时候写、三层校验如何配合”汇总到 `docs/project-retrospective.md` 并由学习者个人复述。
- **自动收集规则**：以后学习者亲手完成的关键函数、关键测试、重要数据流、业务真实性判断，以及已经问清楚的核心概念，由 AI 在验证后自动写入学习账本；普通拼写错误、重复 fixture 和机械接线不单独收集。阶段结束仍按“做了什么、收获了什么、证据、遗留问题、概念问题”汇总。

## 阶段 7B：L1 完整数据流与趋势稳定性

- **完整数据流**：用户输入品类 → Tavily 查公开资料 → DeepSeek 理解资料并生成搜索词 → SerpApi 用这些词搜索 Amazon/Walmart → 普通代码完成字段清洗与映射、利润计算和固定评分。DeepSeek 是品类理解与搜索增强层，不直接连接电商平台，也不负责决定财务结果。
- **趋势偶发 502 的处理**：本次页面曾显示“SerpApi 趋势连接失败”，但随后用同一关键词直接请求本地 `/api/trend` 能返回 200 和 24 个月趋势点，说明 Key、参数和映射链路可用，失败更符合一次短暂连接波动。趋势查询是只读请求，因此后端仅对连接失败或超时对应的 502/504 自动重试一次；鉴权、额度、参数等其他错误不重试，避免掩盖真实问题或无限消耗额度。
- **搜索示例的意义**：搜索框下方现在直接展示上装、下装、裙装、运动服、外套和细分人群的英文示例。它不是限制可搜索范围，而是告诉第一次使用的人应该输入类似 `hoodies`、`yoga pants`、`plus size jeans` 的英文服装品类，降低空白输入框带来的理解成本。
- **验证证据**：新增趋势瞬时失败后第二次成功的自动测试；重启 BFF 后真实 `/api/trend` 请求返回 HTTP 200 和 24 个趋势点；全量测试 71/71、类型检查、diff 检查和正式构建全部通过。
- **学习者阶段复述**：学习者已在侧边聊天完成 L1 数据流复述。主线是浏览器输入 → BFF 保护密钥并调用外部服务 → Tavily 找网页证据 → DeepSeek 生成结构化画像和搜索词 → SerpApi 搜 Amazon/Walmart 商品及 Google Trends，TikTok 官方 Affiliate API 搜开放联盟商品 → 各渠道清洗、映射为统一商品 → Pipeline 用确定性代码计算利润、评分、可信度和风险 → 浏览器展示带来源且可诚实降级的报告。TikTok 接口、签名和映射已经实现，但未取得 Seller 授权凭据，因此只能算代码接通、不能算 live 验收完成。

## 阶段 7B：L2 按渠道利润

- **发现的核心问题**：当前 `CategoryQuery` 只有一份全局 `CostInputs`，评分又把 Amazon 与 Walmart 的全部售价合并后只算一次利润。这会让两个渠道共用一个佣金率，也看不到各渠道售价和利润差异，因此只能算“整个样本的一次估算”，不能称为“分别计算平台利润”。
- **官方费率边界**：美国服装品类的推荐佣金不是永远固定一个数，而且会随售价档位变化。售价高于 20 美元时 Amazon Clothing and Accessories 为 17%，Walmart Apparel and Accessories 为 15%；TikTok 平台费按 6% 估算，并额外扣除 Affiliate API 每件商品返回的创作者联盟佣金。Amazon 推荐费还要应用每件最低 0.30 美元，不能只乘百分比。
- **最小真实方案**：采购成本、头程和广告率仍由学习者输入；平台佣金由“渠道 + 中位售价”规则计算。Pipeline 分别筛选每个渠道的 listing，分别求中位售价和单位利润，再展示各渠道利润；综合评分暂用已实现渠道利润中的保守值，避免平均数掩盖某个平台亏损。

## 阶段 7B：TikTok 官方商品入口

- **为什么不能直接用普通 TikTok API**：TikTok Shop 的普通 Seller Product Search 只能读取已经授权店铺自己的商品，不适合竞品选品；Research API 的 Shop 商品数据面向合格的非商业研究者，且当前主要是欧盟店铺，也不适合本商业演示。
- **最终选择的数据源**：官方 `Seller Search Affiliate Open Collaboration Product` 接口能按关键词搜索 TikTok Shop Affiliate Product Marketplace 中开放合作的商品，返回标题、销售价、币种、累计销量、店铺和详情链接。它覆盖的是开放联盟商品，不等于 TikTok Shop 全量商品，报告必须保留这个覆盖边界。
- **权限边界**：真实请求需要 Partner 应用、`seller.affiliate_collaboration.read` scope、Seller OAuth 授权，以及 app key、app secret、access token、shop cipher。四项密钥只放后端 `.env`；请求使用 HMAC-SHA256 签名，前端不能接触密钥。
- **清洗和映射**：TikTok 适配器过滤空标题、非正数价格和重复商品，再映射为统一 `CompetitorListing`。`units_sold` 记录为 `lifetimeSales`（累计销量），不能放进 `monthlySales` 冒充月销；店铺名也不冒充品牌。
- **失败方式**：只有 TikTok 渠道且未授权时返回 503；与 Amazon/Walmart 一起选择时保留其他渠道商品，并把 TikTok 标成 error。这样“授权缺失”不会拖垮已成功渠道，也不会伪造 TikTok 结果。
- **当前证据**：官方字段结构、签名固定夹具、请求构造、映射、缺凭据和混合渠道降级共 13 项定向测试全部通过，类型检查与 diff 检查通过；由于当前没有真实 TikTok Seller 授权凭据，live 调用仍未验收，不能称为三平台 live 全部完成。

## 阶段 7B：L2 按渠道利润完成

- **做了什么**：学习者明确本轮不参与 L2 实现，AI新增 `resolveUsApparelReferralRate` 和 `calculateChannelEconomics`，按渠道分别取中位售价、匹配美国服装佣金档位、计算平台佣金、广告成本、单件利润和毛利率。搜索表单不再要求用户手填一份全局平台佣金。
- **核心业务规则**：售价不高于 15 美元时 Amazon/Walmart 佣金 5%，15～20 美元为 10%；高于 20 美元时 Amazon 17%、Walmart 15%；TikTok 使用 6% 平台费并另扣 API 返回的联盟佣金。Amazon 低价商品取百分比佣金与每件最低 0.30 美元中的较大值。页面明确称为“简化单件毛利估算”，不含履约或末端配送、仓储、退货损耗、税费与促销，不能当作最终净利润。
- **保守评分**：页面同时展示每个平台的中位售价和利润；综合毛利维度使用已取得渠道中最低的毛利率，避免 TikTok 高毛利把 Amazon 的低毛利或亏损平均掉。渠道没有真实商品时不生成该渠道利润。
- **固定证据**：售价 40、采购 12、头程 4、广告 10%、TikTok 联盟佣金 12% 时，Amazon 平台佣金 6.80、利润 13.20、毛利率 33%；Walmart 平台佣金 6、利润 14、毛利率 35%；TikTok 平台费 2.40、联盟佣金 4.80、利润 12.80、毛利率 32%。没有 TikTok 联盟佣金字段时不生成可比较利润。全量自动测试 83/83、类型检查和正式构建通过。
- **分工真实性**：L2 核心函数、数据合同、页面和测试均由 AI 完成，不记录为学习者亲手实现；学习者只需查看核心函数和理解“为什么必须按渠道拆分”。

## 阶段 7B：DeepSeek 证据洞察增强

- **为什么选择这个功能**：模型除了扩展搜索词，最适合处理普通公式难以完成的文字理解。这里让 DeepSeek 从 Tavily 的公开证据中提取目标人群、购买驱动和待验证问题，回答“谁可能买、为什么买、下一步要验证什么”；利润、费率、评分和渠道状态继续由确定性代码负责。
- **为什么不让模型直接推荐选品**：模型可能产生看似合理但没有数据支持的结论。新字段仍受 Prompt、JSON Schema 和 validator 三层约束，`audiences` 和 `purchaseDrivers` 证据不足时必须为空，`validationQuestions` 明确是问题而不是事实，并继续使用白名单 evidence ID。
- **成本与降级**：新字段加入原有一次画像调用，没有增加第二次 DeepSeek 请求；缺 Key、超时或输出不合格时，确定性画像返回空人群、空购买驱动和两条通用验证问题，并标记 degraded。
- **真实证据**：一次脱敏 live 请求返回 `mode=deepseek`、`degraded=false`，获得 3 个目标人群、5 个购买驱动、3 个待验证问题和 2 条服务端引用。自动测试覆盖合法新字段、未知证据、非英文搜索词和确定性降级。
- **独立 Review 后的证据升级**：原实现只给整份画像保存一组 evidence IDs，无法证明某一条人群或购买驱动到底来自哪条资料。现在每条洞察先由模型返回 `{ text, evidenceIds }`，validator 单独检查这些 ID 是否属于本次真实输入，BFF 再换成可点击 citation；新版 live 请求得到 3 条人群、5 条购买驱动、3 个待验证问题，首条人群和购买驱动都各自带 1 个来源。JSON Schema 只能保证结构和 ID 字段存在，仍不能自动判断文字是否真的被网页语义支持，因此最终还需要人工 Review。

## 后端架构与数据存储

- **BFF 不是框架**：BFF（Backend for Frontend）是一种架构思想，表示“为当前前端专门提供接口和数据形状的后端层”；Node.js 是运行 JavaScript 后端代码的环境。本项目使用 Node.js 原生 HTTP 能力实现 BFF，没有使用 Express 或 NestJS。BFF 同样可以用 Java、Python、Go 等技术实现。
- **本项目算前后端分离**：前端由 Vue/Vite 运行在 `5273`，BFF 后端由 Node.js 运行在 `8787`，两者通过 HTTP API 通信，因此在职责和运行时上属于前后端分离；但两部分代码放在同一个 Git 仓库，并通过一条 `npm run dev` 命令同时启动，所以属于“同仓库管理、前后端分离”，不是两个独立仓库。
- **浏览器当前保存的具体内容**：`src/stores/library.ts` 把完整 `SelectionReport[]` 转成 JSON，使用键 `product-picker:reports` 写入 `localStorage`。内容包括用户查询、市场与渠道、品类画像、商品和价格、趋势、成本利润、评分风险、引用、报告 ID 与创建时间。刷新页面或重启浏览器后通常仍在，但只属于当前设备、浏览器和站点；清除浏览器数据、换设备或隐私模式可能丢失，也不能供多人共享。
- **本地报告存储不等于 API 缓存**：当前 `localStorage` 保存的是已经生成的最终报告，不会让 Tavily、SerpApi 或 DeepSeek 的相同请求自动复用结果。真正的接口缓存需要按请求参数生成 cache key，保存第三方响应和过期时间，在命中时跳过外部调用；它属于后续 L4 能力。
- **前后端一体是什么**：页面、服务端逻辑和接口通常由同一个全栈应用统一组织、构建和部署，例如 Next.js、Nuxt 或服务端模板应用。页面和接口常使用同一域名、版本一起发布，适合快速开发和较小产品，但两层通常耦合更紧。
- **前后端分离是什么**：前端作为独立页面应用运行，后端作为独立 API 服务运行，双方通过 HTTP/JSON 合同通信，可以分别开发、测试和部署，也更容易给网页、移动端等多个客户端复用后端。本项目的 Vue 前端与 Node.js BFF 就是这种形式。
- **判断标准不是仓库和启动命令**：代码放在一个仓库或通过一条命令同时启动，不代表前后端一体；关键要看前端与后端是否是独立运行单元、是否通过明确 API 合同通信。当前项目是同仓库、两进程、HTTP 通信，所以属于前后端分离。
- **数据库负责什么**：正式数据库用于长期、可靠地保存用户与权限、历史查询任务、选品报告、证据引用、任务状态和成本配置。当前 Demo 把报告放在浏览器本地存储中，换设备、清浏览器数据或服务端协作时都不可靠，因此不能替代生产数据库。
- **PostgreSQL 与 Redis 的区别**：PostgreSQL 适合长期保存需要查询和关联的业务数据；Redis 主要用于短期缓存 Tavily、SerpApi、DeepSeek 结果，减少重复请求、等待时间和 API 费用。Redis 不应替代全部正式数据库；面试演示版可以先实现内存缓存或 Redis，生产版通常需要 PostgreSQL 与 Redis 配合。

## L1 全链路与关键技术复述

- **Pipeline 是流程编排器**：它不是搜索工具，也不是大模型。它规定 discover、market、trend、reviews、verdict 等步骤的依赖和执行顺序，保存每一步的结果，并允许不关键的步骤失败后诚实降级。人话就是“负责安排整条流水线怎么跑”。
- **BFF 是前端专用后端**：BFF 不是一个 search 函数，而是运行在 Node.js 中的整层后端。浏览器只把请求发给 BFF；BFF 保护 API Key、校验输入、调用 Tavily、SerpApi、DeepSeek 和 TikTok 官方接口，再把不同返回整理成前端需要的 JSON。L3 加入 `/api/reviews` 后，前端可调用的核心路由共有五个：`/api/search`、`/api/profile`、`/api/listings`、`/api/trend`、`/api/reviews`。其中 `/api/profile` 内部才会调用 DeepSeek。
- **Tavily 与 SerpApi 的分工**：Tavily 是通用网页搜索工具，会从多个公开网页返回 `title`、`url`、`snippet`，为品类画像提供可追溯文字证据；它不是只打开某一个网页。SerpApi 是结构化搜索接口，本项目用它获取 Amazon/Walmart 商品、Google Trends 趋势以及 Amazon/Walmart 评论。DeepSeek 不直接连接三个电商平台。
- **完整数据流**：浏览器提交品类、渠道和成本假设 → BFF 校验并保护密钥 → Tavily 返回公开网页证据 → DeepSeek 把关键词和证据整理为结构化品类画像及英文搜索词 → SerpApi 搜索 Amazon/Walmart，TikTok 官方 Affiliate API 在有合法授权时搜索开放联盟商品 → 各平台适配器用 `filter + map` 清洗无效标题、非正数价格和重复项，再映射成统一 `CompetitorListing` → Pipeline 用普通代码计算需求代理、趋势、分渠道利润、评分、可信度和风险 → 浏览器显示带来源且能诚实降级的报告。
- **Prompt、JSON Schema、validator 与人工 Review**：Prompt 告诉模型“要做什么、不能编什么、只能输出什么”；JSON Schema 是机器可读的数据合同，检查字段和类型的外形；validator 检查 evidence ID 是否属于本次真实输入等业务合法性；人工 Review 最后判断证据文字是否真的支持模型结论。三层不能互相替代。
- **清洗与映射**：清洗删除空标题、无效价格、重复商品等不能进入业务的数据；映射把 Amazon、Walmart、TikTok 各自不同的原始字段翻译成项目统一字段。统一后，利润和评分代码不需要分别理解三个平台。

## 阶段 7B：L3 真实评论与待复核痛点完成

- **做了什么**：BFF 新增 `/api/reviews`，通过 SerpApi 的 Amazon Product 和 Walmart Product Reviews 接口，从每个可用渠道选择一个评价数较高的代表商品，最多保留 20 条公开评论。Pipeline 只对低评分评论中的明确负面表达做规则归类，并保存支持该主题的 review ID；报告展示评论渠道、评分、证据摘录、商品来源和抓取时间。
- **为什么 Walmart 要单独保存 `reviewProductId`**：Walmart 商品搜索结果中的 `product_id` 用于 listing 身份，评论接口要求数字形式的 `us_item_id`。两者用途不同，不能看到一个数字就猜是评论 ID；适配器因此把 `us_item_id` 单独保存为 `reviewProductId`，评论接口只读取这个字段。
- **TikTok 边界**：学习者决定本阶段跳过 TikTok 评论。系统不会向不存在或未授权的接口发请求，也不会用 fixture 冒充真实评论；页面明确显示 `TikTok 竞品消费者评论本阶段不接入`。这不是 Amazon/Walmart 评论链路失败，而是被诚实标注的产品范围。
- **为什么叫“待复核痛点”**：规则只把低评分评论中的 `runs small`、`too thin`、`zipper broke` 等明确负面短语归入尺码、面料、做工、舒适度或外观主题，并保留原评论 ID。关键词规则仍可能误解 `not too tight` 一类否定表达，因此它只产生人工 Review 候选，不生成“整个品类普遍存在该问题”的确定事实。
- **隐私与证据边界**：系统不保存评论者姓名、头像或主页，只保存最多 300 个字符的必要证据摘录。每个渠道只取一个代表商品，小样本不能代表整个品类；页面必须明确提示这一点。
- **独立 Review 的影响**：Reviewer 发现并推动修复五项问题：Walmart 商品 ID 与评论 ID 混用、正面词可能误判痛点、评论正文保存过长、页面隐藏渠道错误、TikTok-only 请求错误依赖 SerpApi Key。修复后 Reviewer 确认没有剩余 P1/P2。
- **证据**：真实烟测取得 Amazon 8 条、Walmart 10 条，共 18 条带商品来源的评论，并发现 3 条低评分样本；最终全量自动测试 97/97，TypeScript 类型检查、`git diff --check` 和生产构建通过。
- **遗留问题**：TikTok 竞品评论明确不在本阶段范围；`not too tight` 等复杂否定表达可能进入待复核候选，后续可增加否定前缀规则或语义分类，但当前人工复核提示已经阻止它被包装成确定事实。
- **概念问题**：为什么第三方商品 ID 和评论 API ID 不能混用？为什么低评分加关键词只能生成待复核主题，不能证明品类普遍痛点？为什么评论证据要限制样本数、文本长度并保留来源？
- **分工真实性**：L3 的接口、映射、痛点规则、页面、测试、live 烟测和独立 Review 均由 AI 完成；学习者本阶段作出的关键产品决定是跳过 TikTok 评论并要求明确标注，不记录为亲手编码。下一阶段 L4 恢复学习分工，学习者只处理缓存是否命中/过期这一项关键判断，AI完成机械接线和测试。

## 阶段 7B：L4 TTL 缓存与 SSE 实时进度

- **缓存是什么**：缓存是在一段有效时间内保存第三方 API 的成功结果。相同输入再次出现时直接读取保存结果，不再调用 Tavily、DeepSeek 或 SerpApi；超过 TTL 后缓存失效，程序重新联网。它和浏览器 `localStorage` 不同：前者减少 API 调用，后者只是保存已经完成的报告。
- **核心判断**：先根据接口类型和规范化输入生成 cache key，再检查 key 是否存在且 `expiresAt > now`。满足就是 hit；不存在或过期就是 miss，调用真实 loader，只有成功且符合业务条件的结果才写入缓存。错误、Abort、DeepSeek 降级画像和不完整渠道结果不缓存，避免把暂时故障冻结成“正常数据”。
- **当前实现边界**：`TtlCache` 在 BFF 内存中保存最多 150 项，并使用 `structuredClone` 防止 Pipeline 修改共享缓存对象。公开网页保存 30 分钟、商品 15 分钟、趋势 6 小时、合格 DeepSeek 画像 12 小时、评论 30 分钟。BFF 重启后清空，多实例不共享；生产环境应换 Redis。
- **SSE 是什么**：SSE（Server-Sent Events，服务端推送事件）让浏览器建立一个持续的 HTTP 连接，BFF 使用 `text/event-stream` 连续发送进度。它是单向的“后端 → 浏览器”，正适合调研任务进度；用户提交和取消仍使用普通 POST/DELETE，不需要 WebSocket。
- **为什么要移动 live Pipeline**：原 Pipeline 在浏览器执行，本来就能本地更新进度；如果 BFF 只额外发送几条 SSE，会变成重复展示。现在 live 模式由 `POST /api/runs` 创建后端任务，`GET /api/runs/:id/events` 推送同一份 Pipeline 事件，`GET /result` 在完成后读取结果，`DELETE /api/runs/:id` 取消。mock 仍在浏览器运行，避免离线演示依赖后端。
- **重连与竞态**：任务注册表为每条事件分配递增 ID，并保留最近 100 条。EventSource 初次连接会重放任务开始后已经发生的事件；断线重连通过 `Last-Event-ID` 只补缺失部分。每 15 秒发送一次注释心跳防止代理误关连接，心跳不占业务事件 ID；关闭 SSE 连接不会自动取消任务。
- **真实证据**：第一次 `blouses` live 查询收到 36 个 SSE 事件和 29 次步骤更新，5 类资源全部 miss，得到 133 个 listing、18 条评论和 `watch` 报告；第二次完全相同查询 5/5 全部 hit、0 miss，返回同样数据，证明没有重复第三方外呼。缓存 hit/miss、TTL 过期、loader 失败、对象克隆、容量淘汰、事件重放、取消和前端最终结果均有自动测试。
- **分工真实性**：缓存核心判断和 SSE 全部由 AI 实现。学习者原计划亲手 Review 命中/过期逻辑，但本轮明确要求 AI 把计划全部做完，因此改为最终由 AI 带着走读；不把这些代码记为学习者亲手完成。

## 阶段 7B 最终收尾

- **做了什么**：L1 到 L4 与 SSE 均已完成；live Pipeline 在 BFF 中执行，前端通过 EventSource 接收实时进度；Amazon/Walmart 评论、成本利润、证据洞察和缓存均已接入最终报告。
- **收获了什么**：第三方数据必须先清洗映射；模型输出必须经过 Schema、validator 和人工 Review；财务结果用确定性代码计算；长任务用后端任务注册表与 SSE 推进度；成功且完整的外部结果才适合缓存。
- **证据**：最终自动测试 117/117、类型检查、diff 检查和生产构建通过；两次相同 live 查询验证第一次 5 类缓存 miss、第二次 5/5 hit；BFF 仅监听本机回环地址。
- **遗留问题**：TikTok 商品 live 仍需要 Seller/Partner 合法授权；TikTok 评论明确不接入；内存缓存和任务在 BFF 重启后丢失；报告仍是浏览器本地保存，不是生产数据库。
- **概念问题**：为什么缓存 key 必须与 loader 的真实输入一致？为什么 HTTP 202 不能当成最终结果？为什么 SSE 断开不应默认等于用户取消？为什么小样本评论只能生成待复核痛点？
- **分工真实性**：学习者亲手完成早期 Amazon/Walmart 映射、Walmart 测试、成本核心、DeepSeek Prompt 与 validator 关键校验，并决定跳过 TikTok 评论和追加 SSE；L2、L3、L4、SSE 的其余实现、测试、Review 和交付由 AI 完成，最终由 AI 带学习者走读，不冒充学习者亲手编码。
